# 验收标准

改动只有满足以下每一条才算完成。
**跑过的检查写明结果；没跑的检查写「未跑」，不许省略。**
（这条不是道德要求，是格式要求——因为格式能被检查，道德不能。）

## 一、验收六条

### 1. 有一个「没有这个改动就会失败」的测试

BinviaCheck 的断言就是这条的载体：新增或修改共享行为（路由、认证、重试、流式聚合、配置解析）时，
在 `Sources/BinviaCheck/main.swift` 加断言，**把旧代码放回去跑必须出现真的 `FAIL` 并点名具体行为**。
编译错误、跳过、断言缺失都不算。

反向验证：写完之后**手工把改动改坏一处**，确认测试变红，再还原确认变绿。

> 注意：本机无 XCTest、无 `swift test`，BinviaCheck 也**不支持按用例筛选**——
> 要跑子集只能临时注释掉入口处的 `run(...)` 调用。所以「跑一个用例」这个动作很贵，
> 反向验证请优先用「改坏一处 + 跑全量」的方式。

### 2. 测试在沙箱里跑

测试入口在 `Sources/BinviaCheck/main.swift` 末尾做了隔离：

- `BINVIA_CONFIG` 指向不存在的临时路径（第 ~5043 行）；
- 凭据环境变量（`DEEPSEEK_API_KEY`、`BINVIA_API_KEY`、`ROUTER_API_KEY`、`OMNIROUTE_API_KEY` 等）
  在用例内 `unsetenv` / `setenv`，并在 `defer` 里还原。

**绝不读写真实用户的配置、凭证或数据**：`~/.config/binvia/config.json` 是敏感路径，
新测试必须沿用 `BINVIA_CONFIG` 覆盖的写法，不要直接构造默认配置路径。

### 3. 构建与全量套件

- 构建：`swift build`
- 全量测试：`make test`（= `swift run BinviaCheck`，退出码 0 = 全绿，1 = 有失败）

**测试数量不要写死在文档或 CI 注释里**——它会腐坏。当前真实值以 `swift run BinviaCheck`
末行输出为准（历史上 698 / 647 / 591 / 464 四种数字曾同时存在且都不对，见 `LESSONS.md`）。

### 4. 反向验证（改坏看红）

上一节第 1 条的配套动作，单独列出来因为它最容易被跳过：

- 把这次的核心改动**手工改坏一处**（不是删掉整个函数）
- 跑 `make test`，确认它变红
- 还原，确认它变绿
- 在提交信息里写明「改坏了什么、红成什么样」

### 5. 尽可能真实使用

能对真实环境跑的，必须真跑一次：真配置格式、真实的上下游、真实客户端。

- **服务端 / API 改动**：`make run` 起服务，用 `curl` 打改动到的端点
  （`/v1/chat/completions`、`/v1/models`、`/v1/usage`、`/v1/health`）。
  供应商可用性用 `swift run BinviaCLI test <provider|alias>`。
- **GUI 改动**：`swift run BinviaApp --smoke-test`（启动服务器 → 健康检查 → 停服）。
  布局类改动另见 `LESSONS.md` 里的进程内视图树验证法。

> 已知限制（2026-10-13 实测）：本机只装了 Command Line Tools、无 Xcode，
> `BinviaCore` / `BinviaServer` / `BinviaCLI` / `BinviaCheck` 都能构建、`make test` 844 项全绿；
> 但 **`BinviaApp` 无法在本机构建**——SwiftUI 的 `@State` 等宏需要 `SwiftUIMacros` 插件，
> 该插件只随 Xcode 提供（报错：`plugin for module 'SwiftUIMacros' not found`）。
> 因此 GUI 改动的真实验证要么在有 Xcode 的机器上做，要么依赖 CI（`macos-26` runner 自带 Xcode）。
> **跑不了的，明说「未验证」，不要告诉用户它能用。**

### 6. 只改这次目标需要的东西

顺手发现的问题**另开一次提交**。夹带的改动会让审查无法判断哪一部分是本次要验证的。

GUI 类改动补充：

- 改了设置面板/列表的增删改逻辑 → 读 `LESSONS.md` 的 SwiftUI 条目，注意 `ForEach` 的 `id` 稳定性；
- 改了 `ProviderDescriptor` / 注册表 / 路由 → 跑全量 `make test`，不要只跑相关断言；
- 改到 `docs/` 里已有分析报告的模块 → 先读对应报告再改代码。

## 二、提交信息

三段式，缺一段都算没写完：

```
<scope>: <用户看到的变化，用行为描述，不用实现描述>

为什么：<谁报的 / 什么场景触发的 / 不这么改会怎样>
改了什么：<哪些行为面变了；边界在哪；哪些相邻情况保持不变>
跑了什么：<具体命令 + 具体结果数字>
没试过：<明确列出没验证的部分>
```

要求：

- **标题用行为描述**，不要写「重构 X」「优化 Y」。写「<在什么情况下> <用户看到什么变化>」。
  历史里 42 次 `update：...` 这种标题无法回溯，不要继续这个习惯。
- **数字要具体**：不写「测试通过」，写「`make test` 通过，844 项断言，0 失败」。
  具体数字无法伪造，含糊描述可以。（上面这个数字只是举例，别照抄——它会变，
  以你那次 `make test` 的实际输出为准。）
- **「没试过」是必填项**。没验证的部分写「未跑」，不省略。
  这是后面审查判断「这次改动能不能信」的唯一依据。
- 大改动（改了多个文件或行为面）必须有 body。只改错别字可以只有标题。

> 现状提示（2026-10-13 统计）：最近 40 个提交里只有 **10 个**有 ≥3 行正文，
> 即约 75% 的提交缺 body。这条规范目前是「新增的要求」，不是在描述既有习惯。

## 三、复盘

### 什么时候复盘

**发版前**（对应 `version.env` 的 `MARKETING_VERSION` 提升 / 打 tag 之前），
或每约 20 个提交。

**额外触发条件**：一次任务里出现**返工**（同一个东西改了两次以上）→ 立刻复盘一次。

> 为什么选这个节奏：本项目发版很密（40 个提交里有 19 次动了 `version.env`、12 次是发版/文档提交），
> 「发版前」是一个已经存在的仪式，挂上去成本最低，且天然有 ~20 个提交的间隔。

### 怎么复盘

用一个独立会话（或独立 Agent）来读，不要用正在改代码的那个——它知道自己当时的想法，会替自己辩护。提示词：

```
读最近 N 个提交的完整信息和 diff。回答三个问题：

1. 哪些是「修完又坏」或「改完又改」的？根因是什么？
2. 哪些改动其实不该合进来？（夹带、超出范围、没验证）
3. 哪些验证做太薄？（只说"应该没问题"、没真跑、没反向验证）

对每个发现，写成一条错题追加到 LESSONS.md：
规则（祈使句）→ 症状 → 根因 → 证据（commit + 事件）。
已存在的错题，复发次数 +1。

最后：有复发 >= 3 次的，移进 docs/code-standards.md，从错题本删掉。

只报你有证据的发现。没发现就明说没有——不要为了凑数编造错题。
```

最后一句很重要：被要求「找问题」的 Agent 一定会找出问题，包括不存在的问题。
编造的错题比没有错题更糟——它教了一条与现实不符的规则，而且会烧掉读者对整份文件的信任。

**用独立上下文跑**（新会话，不是改代码的那个）。自己审自己会替自己辩护。

如果实在没有独立上下文，也照跑，但**只报可机械核对的事实**
（`git log` / `git show` 里能直接看到的：标题和 diff 不符、body 声称修了但代码没动），
跳过「验证够不够厚」这类判断。并在输出里明说这次是自审。

### 毕业规则

一条错题被**独立踩到 3 次** → 说明光靠「读一遍」拦不住 → 升级成常驻标准。

- 标准正文写进本文件的「四、已毕业的规矩」
- 从 `LESSONS.md` 删掉正文，只留一行指针
- 「独立踩到」指分开的时间点，同一次任务里犯两回算一次
